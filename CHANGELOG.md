## Unreleased

### English

- **Probe F1b (layouts), crates `fs-forms-layout`, `fs-forms-exchange`, `fs-forms-store`** (first cut, written with Claude). Open points, stated plainly: overlay ops `Insert` and `Move` are stored but NOT applied (they give conflict `field-unknown`); the import side of the live provider check (K67) is not built, only `resolve` runs it (without a provider `resolve` now says `provider-unchecked`); a refused write of an AI acting on behalf is not logged (K78, the log has no word for it); the update with a failing hook in the middle (K93) has no test, the memory store is atomic by copy; the database adapter (`DbLayoutStore`), the serving of the layouts, emergency mode and `repair` are still not written (state of 0.0.3: the contract `layouts.capnp` exists in fs-interfaces v0.0.28 and fs-objects v5 is pinned at v0.0.8, but no adapter uses them yet; `spec.rs` holds stand-ins with its shape); the exchange does not write filters of views or overlay files yet.
- Tables `forms_*` run on the real engine (turso 0.8.3, as dev-dependency of `fs-forms-store`): `forms_binding.from` is renamed `bind_from` (`from` is an SQL keyword and the fs-objects v5 renderer does not quote), and the two checks of the form `CHECK ((x IN (...)) = (...))` are written out as `A AND B OR NOT A AND NOT B`, because turso 0.8.3 refuses exactly this form ("cannot determine type of expression in CHECK"). The plain forms `(A) = (B)` and sums of booleans are accepted by the engine (measured by the reviewer: correction of an earlier, too wide statement). All the other checks were rewritten as well and are equivalent in three-valued logic.
- Overlays (round 4): after every op the result passes the same `check` as any description (local rules, catalog, limits); a person's overlay can never widen a scheme allowlist (`allowlist-widened`; only the instance or the package itself may); a source can only be removed when it is the last one (a removal in the middle would renumber the sources and point blocks at another source). Security allowlists in this crate: the scheme list of a field use (restrict only for a person), the fixed never-list (`javascript`, `vbscript`: nobody may add them), the block catalog and `repeat` per slot (checked again after every op), the technical `nth < 16`, the limits, and the instance locks. Command and workflow names are only names here: whether a person may use them is decided by the host.
- Open points found by the review of round 4 (stated plainly): (K1) conflicts are computed against the original alone when an overlay is written and against the whole stack in `resolve`; example: the instance removes source 3, a person removes source 2 -> the stored conflict says `result-invalid`, yet the op takes effect in `resolve`. It is safe (`resolve` checks everything) but the stored conflict can mislead; to be fixed by computing conflicts against the stack or by saying so in the design. (K2) A person can set the `path` of a field binding; a binding WITHOUT a scheme list means "nothing is allowed" (fail closed): the host must treat a missing list that way (the test belongs to the host order, not to this crate). (K3) `text_bytes_max` is applied to messages only. The signature of `apply` changed in round 4 (catalog and limits are passed in): F2 and H1 must follow.
- `LayoutCode` has 45 codes (new at the END of the list: `menu-invalid`, `source-unknown`), with German and English texts for all of them in `fs-forms-layout/src/texts/`.
- `LayoutDoc::check` now runs the same local rules as the tables (menu pairs, source numbers, lower-case schemes, ranges with both bounds) and `apply` runs them after every overlay op (an overlay can no longer set `javascript`).
- New crate `fs-forms-bind` (draft): the pure build plan `Bind::build(&Resolved, &dyn Catalog, &Providers) -> Plan`; every problem is a `PartLock` on the smallest part (`bind-error-locked`) or a window notice. Commands decide visibility by right first (hidden without right, "coming" only with right), the keymap is the real `fs_components_commands::Keymap`, the standard menus are an input of the host, the plan digest is SHA-256 over a fixed byte form (`sha2 0.10`, same version as in the lock). PlanSuite with 12 rules and 12 mutants; MF2 texts de + en for 18 codes; Windows job for the crate.
- **Transition (falls away with the cascade):** `reserved()` and `list_only()` in `fs-forms-bind` are a local copy; `RESERVED` becomes a constant in `fs-components-commands` and bind uses it. Until then the probe pins `fs-components-commands` to tag `v0.0.29`; the cascade lifts all fs-components crates to one tag.
- The crate `fs-forms-methods` is gone: the ten counting methods are the library `fs-tally` (own repo, tests moved with it). The box logic (`Lane`, token hash, OS randomness) is the library `fs-ballot`; `fs-forms-core` keeps its two lanes as `fs_ballot::Lane<Ballot, Signals>` (`Signals` implements `fs_ballot::Meta`). Behaviour and stored JSON field names are unchanged; the legacy single lane of box 0.1.0 now also keeps its pending pattern counts.
- **Pins:** `fs-tally` and `fs-ballot` are pinned to their tag `v0.0.1`. `.fs-lock-sources.toml` stays strict.
- **Test note (49.7-day trap, fixed):** `tests/anonymous.rs` used to search the raw box for the current year (`2026-`). The ids of the box are UUIDv7, whose first hex digits are the millisecond clock; in a window of 65.5 s every 49.7 days (next: 2026-11-28 03:14:51 UTC) such an id contained `2026-` and the test was always red, otherwise by chance about once in 33,000 runs with two different ids in the box (about 1 in 65,000 with one id). It now blanks out every real UUID (8-4-4-4-12), then reads every `dddd-d` start of a date in any spelling (`2026-11-5`, `2026-11`, `2026-322` too) and requires each one to read `1970-01-01`; ids can never match. Known gaps, shared with the old test and left for a follow-up card: a time without a date, Unix seconds, the compact ISO form `20261118T100000Z`. The two waiting tests of `invite_lock.rs` now fail after 30 s instead of hanging if a lock is never given back. The wait of the two `handshake.rs` tests for the server is now a connection attempt through the transport of `fs-rpc` (retry with short pauses up to 30 s, then a red test with the last error in the message) instead of `socket.exists()`: a bound name is not a listening server (load), and on Windows there is no socket file (named pipe); each crate has the helper in `tests/support/mod.rs` and tests of the failure case. On the Windows runner the test `both_pages_are_drawn_at_the_size_asked_and_differ` is ignored with a reason (wgpu Validation Error on windows-2022 without a GPU adapter, not proven to be "no adapter", so the skip condition stays unchanged); it returns when the runner offers a software adapter. The head comment of `windows.yml` now says what it does (whole workspace, Blinc/GPU crates are built too, socket tests run). No product code changed.
- Still open: the box is one JSON document in `fs-objects` (typed columns are the separate step D2b).

- **`fs-forms-run` (host), stack k5-forms-6..8:** the side list of a `workbench` page stands in the region `side` BESIDE the main area (it stood above the board); every part takes the full width of its region and scrolls sideways where it is wider (the board does); padding in pixels (it was in Blinc units, four times too wide). The host asks `fs-components-catalog` which blocks exist (the contract of the pinned tag is read at build time by `build.rs`; the catalog crate of v0.0.30 does not embed it yet): a block the contract does not know is `host-error-block-unknown`, one it knows and the host cannot draw yet `host-error-block-not-built`; the table block to component is now only an assignment block to drawing function. `style = "default"` is the style set for the program (`--style NAME`, preset `admin`, port `StyleSource`), asked at every drawing; a style named in the description is used as named, an unknown name is said (`host-notice-style-unknown`). Not done: `board-detail`, the connection to `fs-forms-bind` and a type catalog, a live trigger for a style change (needs the style change at run time of fs-components main, S1, not in v0.0.30; the shell and the side list are not style aware in v0.0.30, only the board is).

- **Stack k5-h2: the layouts over RPC and the starter.** The crate `fs-layouts-rpc` moved in from fs-rpc 831aa673 (51 files; client `RpcLayouts`, `RpcLayoutAdmin`, `LayoutService`, `ensure_service`); fs-rpc is never tagged with it. Pins: `fs-rpc` v0.0.3, `fs-interfaces` v0.0.28 (the contracts `layouts` and `bind` are its owner files), `fs-forms-layout` by path; every `fs-*` name has one source in `Cargo.lock`. The binary `fs-forms` lost its own starter (-183 lines): it is a thin `Program` over `fs-starter` (codes `forms-error-usage`, `forms-error-serve-failed`). New word `allowlist-widened`; tests `rpc_exact` (time to the millisecond, every filter operator, `bind_capnp`). **`LayoutService` is NOT yet plugged into `fs-forms-server`:** the server still answers only `capabilities` and `supportReport`; the layouts of a program come from a file (`--description`) until the server serves them.
- **Behaviour change:** without an installed frontend manifest (`<XDG_DATA_DIRS>/freesynergy/frontends/forms/simple.metainfo.xml`) the starter now says `frontend-missing`; the package of `fs-forms-simple` (deb and rpm assets) installs that file. The test is in `fs-forms-bin/tests/packaging.rs`; that the release tools resolve the source paths is checked only by the release workflow.
- **Input limits (before foreign packages are loaded):** `read_layout` and `scaffold.toml` take at most `LAYOUT_BYTES_MAX` (1 MiB; `import-invalid` cause `too-big` resp. `layout-too-big`); a symbolic link below the named folder (`scaffold.toml`, `forms/`, a file of it, the layout a blueprint names) is refused with `layout-link-refused` (Linux test; a file swapped between check and read is not covered); an existing but unreadable `scaffold.toml` is `layout-unreadable` instead of being skipped; one description file is checked against `--frontend` and `--extends`.
- **Host:** `--sample-data` says so in the status line (`host-status-sample`, de + en); `build.rs` watches the lock of the workspace and masks the paths it writes (still needs the checkout of the catalog repository: not with `cargo vendor`, until `BlockCatalog::embedded()` of fs-components).

## 0.0.2

### English

- **Window and server (basics, workflow `grundfassung`).** New crates: `fs-forms-server` (the contract `surveys.capnp` draft 0.1 over a local socket through `fs-rpc` v0.0.2; answers `capabilities` with no capability ids and the contract version, and `supportReport`; everything else is `unimplemented`), `fs-forms-client` (connect with the version handshake, `Hello::fetch`, contract check: same main level, minor level of the server not lower), `fs-forms-simple` (the frontend `simple` as a process of its own: name, icon, what works today, what comes, every element locked with "coming soon"; depends only on the client and fs-components v0.0.25), `fs-forms-bin` (the command `fs-forms`: starter, `serve`, `--version`, `--help`).
- **Starter.** `fs-forms` starts or replaces the server (handshake of `fs-rpc`), asks the frontend to check the contract (`--check`, exit code 3 = does not fit) and falls back to the standard frontend `simple` with a visible message; a missing or unfitting server is said in the window.
- **Pins lifted so the tree holds one source per library:** `fs-objects` v0.0.1 to v0.0.6, `fs-interfaces` v0.0.1 to v0.0.27, new `fs-rpc` v0.0.2, `fs-types` v0.0.1 (through them); `.fs-lock-sources.toml` strict. Minimum Rust 1.89 for the workspace. The core and the methods crate are otherwise unchanged.
- **CI:** `check.yml` and `release.yml` call fs-release at `v0.0.10`; .
- The real icon (`packaging/net.freesynergy.Forms.png`, `.desktop`, embedded in the window); `fs-forms` depends on the package `fs-forms-simple` (deb `depends`, rpm `requires`).
- Contract: draft (`surveys.capnp`, not locked). The basics are released with this draft contract.
- Not done: the window shows no surveys (the core is not connected to the server), no way to make or answer a survey, no lease (the server keeps running after the window closes until it is stopped or replaced).
- Tests: `fs-groups-core` left the dev-dependencies (other pins); widening is tested against an in-memory `GroupLookup` until fs-groups has a tag on the same pins.
